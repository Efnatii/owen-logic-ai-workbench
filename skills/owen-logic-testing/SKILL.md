# Owen Logic Testing

## Overview

Use the local OWEN Logic MCP tools to perform non-destructive OWEN Logic checks: find the installation, launch the GUI, list windows/processes, capture screenshots, and run a smoke test. In Codex Desktop these tools may be exposed through `mcp__artifact_tools__` as `owen_logic_*` because the desktop session has a practical MCP-server startup limit; the standalone workspace server is available at `07_TOOLS\r\owen\mcp\owen_logic_server.py`.

## Workflow

1. Inspect the project folder first. Look for `.st`, `.json`, exported OWEN Logic files, screenshots, Python simulations, and existing test reports.
2. When the user asks for a project "from scratch", use `owen_logic_project_create_from_scratch` first and verify `source_policy.copied_existing_owle_as_base=false`. Do not reuse an existing `.owle` as the base unless the user explicitly asks to modify or migrate an existing project.
3. If local simulation tests exist, run them before opening OWEN Logic. Prefer the project's own commands; for this workspace, many PR200 projects use `python -m pytest`.
4. When the user asks to analyze the installed OWEN Logic program files, use `owen_logic_program_file_analysis` first. It is read-only and should report `opened_gui=false`, `opened_serial_port=false`, `opened_network_socket=false`, and `live_device_action_executed=false`.
5. Use the `owen_logic_find_installation` MCP tool to confirm the executable path and version.
6. Use `owen_logic_smoke_test` for a basic GUI check. Pass `project_path` only when the user gives or the workspace clearly contains the intended OWEN Logic project file.
7. When a visual result matters, use `owen_logic_screenshot` and report the absolute PNG path.
8. For focused UI automation, use `owen_logic_focus_window` and `owen_logic_send_hotkey` only for simple, reversible navigation such as opening a file dialog. Avoid device download/upload actions unless the user explicitly asks.
9. Before any COM/IP, download, online-debug, firmware, calibration, device-settings write, replication, or live Modbus action, run `owen_logic_live_device_preflight` and require exact target confirmation plus backup/readback/abort evidence. The preflight tool is plan/check only; it does not execute live-device actions.
10. Report what was verified, what was not verified, and any remaining manual OWEN Logic steps.

## MCP Tools

The preferred callable tools are `owen_logic_*`. In this workspace they are normally reachable via `mcp__artifact_tools__` to avoid exceeding the Codex Desktop MCP startup set. If neither `mcp__artifact_tools__owen_logic_*` nor a standalone `mcp__owen_logic__` namespace is visible in the current session, tell the user Codex may need to restart or reload MCP servers after editing the active `$CODEX_HOME\config.toml` and refreshing any default user-home compatibility mirror.

- `owen_logic_find_installation`: locate `ProgramRelayFBD.exe`, report version, and locate the ProjectJsonConverter executable.
- `owen_logic_program_file_analysis`: read-only analysis of the installed OWEN Logic program files. It summarizes real file counts, `.deps.json`, installed `mapVersion.xml` PR target catalog, `InputOutputModules` XML roots/module keys, help/library catalogs, display embedded resources, firmware files, filename surfaces, compiler/converter assemblies and required MCP tool checks. It never launches GUI, converter runtime, COM/IP, network, or live-device actions.
- `owen_logic_project_create_from_scratch`: create a new ZIP-based `.owle` without copying any source project. It accepts any installed OWEN PR `target_dev_value` from `mapVersion.xml` such as `PR100EA1`, `PR110`, `PR120`, `PR200ADA` or `PR-DEMO`, writes only under scratch/sandbox/local-heavy, builds target-independent FBD variable/logic/constant blocks plus up to two macro documents, and runs static validation. It does not synthesize target-specific hardware I/O modules; use component catalog/archetype tools for those.
- `owen_logic_live_device_preflight`: non-executing preflight for COM/IP, download, online-debug, firmware, calibration, device-settings write, replication, and live Modbus actions. It checks exact target confirmation, project hash evidence, backup/readback plan, abort plan, and refuses to open COM/IP or launch OWEN Logic.
- `owen_logic_project_lifecycle_smoke`: bounded GUI lifecycle smoke on a scratch `.owle` copy. It opens the copy, exercises documented save/save-as/new-project shortcuts, captures screenshots, preserves the source hash, and cleans up the launched process. With explicit opt-in it tries documented `Ctrl+Alt+S` plus safe keyboard-menu Save As routes before an allowed scratch-only file-level Save As fallback. It does not claim semantic GUI Save As dialog completion unless the evidence explicitly verifies a GUI-created `.owle`.
- `owen_logic_project_gui_open_probe`: scratch-only GUI File > Open project dialog probe. It launches OWEN Logic, drives the real Windows file dialog with a scratch `.owle`, restores the clipboard, records process/new-PID/window/screenshot evidence, waits for post-open progress windows, can dismiss safe post-open information/backup/version dialogs, claims project load only after a visible opened-project window matches the scratch path/name, preserves the source hash, and cleans up launched processes. With `exercise_save_as_file_creation=true` it attempts semantic GUI Save As on the actual opened PID and claims completion only when `gui_open_save_as_dialog_verified=true`.
- `owen_logic_project_gui_new_project_probe`: blank-session GUI New Project probe for documented `Ctrl+N`, File > New Project, and toolbar New entrypoints. It records screenshots, process/window samples, Windows Application event-log crash evidence, WPF wizard window evidence, and cleanup status. With `complete_wizard=true` it can select a visible device family such as `ПР200`, click `Создать`, and verify an unsaved in-memory project surface; with `exercise_save_as_file_creation=true` it can then save that fresh project through the real Save As dialog and verify the created `.owle`.

## Project Review

For `.st` files, review them as IEC 61131-3 Structured Text intended for OWEN Logic. Check declarations, timers, trigger logic, state retention, edge cases after power-up, manual/auto priority, alarm reset behavior, and whether comments/test cases match the implementation.

For generated Python simulations, verify that they preserve the intended PLC scan semantics: one scan updates inputs, timers, state, outputs, and diagnostics deterministically. Prefer tests that cover startup state, mode switching, command priority, fault paths, and timing boundaries.

For more detailed testing notes, read `references/workflow.md` only when the task needs deeper guidance. For `.owle` container/model invariants used by headless generation, read `references/owle-format.md`.

## Guardrails

- Keep GUI automation non-destructive by default.
- For from-scratch project creation, a generated file is only acceptable when the evidence says `created_new_owle_zip=true`, `copied_existing_owle_as_base=false`, `gui_used=false`, and validation has zero errors.
- Do not download to a real controller, erase device memory, update firmware, calibrate, write live Modbus values, or change live communication/device settings unless the user explicitly requests that action and `owen_logic_live_device_preflight` has passed for the exact target/action.
- If OWEN Logic is already open, avoid closing it. Work with the existing window and report that it was already running.
